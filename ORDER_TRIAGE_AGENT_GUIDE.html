1 · What the Case Study Expects

NorthPeak Commerce is a fictional mid-market online retailer. Support tickets arrive as raw, unlabelled free text. Three personas drive the requirements:

Marcus
Tier-1 Support Agent
  • ~4 minutes per ticket
  • Needs a ready-to-send draft reply he can approve or lightly edit
  • Needs a clear signal when a ticket is above his authority
  • Should not touch fraud/payment tickets
Priya
Escalations Lead
  • Owns fraud alerts & payment issues — must arrive immediately
  • Also receives premium-tier HIGH/URGENT tickets
  • Must not be paged for routine "where is my order" queries
  • Needs a pre-written escalation summary with urgency context
Dev
Ops Manager
  • Wants every ticket tagged: category + priority
  • Full audit trail — a rationale for every routing decision
  • Queue health metrics at a glance

The Policy the Agent Must Encode

Step 1 — Classify into one of 10 categories

delivery_delay  |  wrong_item     |  damaged        |  refund_request
payment_issue   |  address_change |  cancel_request |  product_question
subscription    |  fraud_alert

Step 2 — Assign priority (base + optional premium bump)

CategoryBase Priority
fraud_alert, payment_issueURGENT
damaged, wrong_itemHIGH
delivery_delay, refund_request, address_change, cancel_requestMEDIUM
product_question, subscriptionLOW
Premium Tier Bump: If customer_tier == "premium", move priority one rung up the ladder — LOW→MEDIUM, MEDIUM→HIGH, HIGH→URGENT. Capped at URGENT. standard and plus keep base priority.

Step 3 — Route (rules applied in this exact order — order matters)

#ConditionRoute
1 category is fraud_alert or payment_issue Priya — always
2 customer_tier is premium AND priority is HIGH or URGENT Priya
3 everything else Marcus — draft reply
The Composition Trap (key rubric test)

ORD-10015 — premium + address_change:
  • Base priority: MEDIUM (address_change base)
  • After premium bump: HIGH
  • Route check on HIGH → Priya ✓

If you evaluate routing before applying the premium bump (checking MEDIUM against the threshold), the result is Marcus — wrong. Priority MUST be fully composed before routing rules are evaluated.

Step 4 — Required outputs per ticket

ForRequired Output
MarcusShort, on-brand draft reply. Never promise a refund the policy hasn't approved.
PriyaEscalation summary — what happened, why it's escalating, urgency level.
DevOne-line rationale for every decision: category, priority computation, route reason.

2 · What Was Implemented

Architecture — LangGraph StateGraph

orders_queue.csv │ ▼ ┌───────────────┐ │ classify │ LLM call → category (10 types), confidence, flags └───────┬───────┘ Structured output via Pydantic │ ▼ ┌───────────────┐ │ route │ Pure Python → priority (base+bump) + route + rationale └───────┬───────┘ policy_engine.py — NO LLM, deterministic │ ┌────┴────┐ ▼ ▼ draft escalate LLM → draft reply (Marcus) OR escalation summary (Priya) └────┬────┘ │ ┌───────▼───────┐ │ audit │ Writes JSONL record → outputs/audit_log.jsonl └───────────────┘ │ END

One conditional edge after route_node: if state["route"] == "marcus" → draft_node; if "priya" → escalate_node. Both paths converge at audit_node.

LLM vs Pure Python — Where Each Is Used

NodeLLM?Why
classify_nodeYesReading free text and inferring intent is a language task
route_nodeNoPure rule table — deterministic, covered by 45 unit tests, no API key needed
draft_nodeYesGenerating warm, on-brand prose needs a language model
escalate_nodeYesSummarising urgency and context for Priya
audit_nodeNoWrites structured JSON — no language needed

Why ChatOpenAI, not ChatAnthropic?

Perficient's Portkey gateway exposes an OpenAI-compatible API (/v1/chat/completions). ChatAnthropic sends requests in Anthropic native format, the gateway returns an OpenAI-format response, and the client tries to iterate a null content field — crashing with TypeError: 'NoneType' object is not iterable. This is the same pattern used in CertMasterAI's generate_with_portkey().

4 · Key Design Decisions

Policy Composition Order

Correct order — must never be swapped:
  1. Look up base priority from the category table
  2. Apply the premium-tier bump (if applicable)
  3. Evaluate routing rules against the final (post-bump) priority

The test test_triage_premium_address_change in tests/test_policy_engine.py pins this as a hard constraint.

Multi-Issue Ticket Rule (Policy Gap)

The policy states "one issue per ticket" but real tickets don't always cooperate. Documented rule: take the category that yields the highest priority after applying the premium bump. On a tie, take the category that appears first in the note (preserves reading order = customer's primary concern). Implemented in policy_engine.resolve_multi_issue().

Customer-Directed Tickets

Customers who write "this is urgent, escalate now" get the same classification as those who don't. The text_note is data, not an instruction. When detected, the customer_directed flag is set in the rationale for Dev to see, but it does not change category or route.

Why Not RAG?

The full escalation policy fits comfortably in the LLM's context window. Embedding it in ChromaDB and retrieving chunks adds latency and a dependency without improving accuracy. If the policy grew to dozens of pages, RAG would be worth it.
